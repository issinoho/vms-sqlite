## D5. The VFS: our own, `$QIO` block I/O, locks through the C RTL on a lock file

**Status:** approved by the user (2026-10-18), option (a); the cross-group lock test is still to run.

**Why SQLite's unix VFS can't be used.** It does its I/O through C RTL descriptors, and on
VMS those are not coherent (p_mp, both compilers, the feature logicals SQLite would set):
- a process that has written a block keeps reading its own copy: after the other process's
  write *and* fsync, each side still read its own stale byte (T2, T2b);
- a process can't read a page another process appended (T3b: `pread` returns 0);
- `fstat` reports 0 for a file being written until fsync (p_misc), and a `pread` past EOF
  moves EOF to that offset at close (p_misc);
- closing a writable descriptor writes its own idea of EOF into the file header, even one
  that never wrote (p_qio Q6: 8192 written back over the 4096 another process set).

Any of these corrupts a database shared by two processes, which is what PHP's FastCGI pool
does. vms-mariadb (D6, D10) worked around the same behaviour inside one process with a
shared descriptor; SQLite's processes are separate, so that does not help here.

**What works: `$QIO` virtual-block I/O on a UFO channel** (p_qio, both compilers): the file
is opened by RMS with `FAB$M_UFO` (RMS gives us the channel and does no I/O of its own),
shared `GET/PUT/UPI`; `IO$_READVBLK`/`IO$_WRITEVBLK` move the data; the end of file is read
and written as the file header's record attributes (`ATR$C_RECATTR`, `IO$_ACCESS` /
`IO$_MODIFY`), and the allocation is extended with `FIB$M_EXTEND`. Between two processes,
writes are seen both ways, the extended size and the new page are seen, a shrink is seen,
and the C RTL's `stat()` agrees afterwards (Q0-Q4). Reads and writes go through XFC, which is
coherent between processes (and across a cluster).

**The VFS** (`overlay/vmsport/os_vms.c`, registered as the default VFS by `sqlite3_os_init`
under `SQLITE_OS_OTHER`, so `sqlite3.c` itself needs no patch for it):
- `xRead`/`xWrite`: `$QIO` by virtual block; writes that don't cover whole 512-byte blocks
  (journal headers, the last page) read and rewrite the edge blocks. SQLite's locks make that
  safe: only the process holding RESERVED or more writes.
- `xFileSize`: the header's EOF; `xTruncate` sets it; writes past EOF extend the allocation in
  chunks and set EOF.
- `xSync`: writes the EOF if it changed. The data needs nothing more: XFC caches writes
  through, so a completed `IO$_WRITEVBLK` is on the disk (to confirm in Phase 1 against the
  node's XFC settings).
- `xDelete`: deletes every version; `xOpen` never creates a second version of a name.
- `xFullPathname`: VMS file specs through `$PARSE` (no `realpath`, p_misc); Unix-style names
  accepted as the C RTL does.
- `xRandomness`, `xSleep`, `xCurrentTime(Int64)`: `SYS$GETTIM`, `usleep`.

**Locks.** SQLite's levels (SHARED, RESERVED, PENDING, EXCLUSIVE) need byte-range-style
locks visible to every process using the database, whatever its account. Options:
- (a) **The C RTL's `fcntl()` locks on a companion lock file** (`<db>-lock`, created with the
  database's protection), taken and released in exact pairs. They exclude between processes,
  privileged or not (p_mp T1 with `NOALL,NETMBX,TMPMBX`), and the C RTL keeps them in the
  system-wide namespace (`C$__<device><fid>`, p_lkns). Exact pairs don't leak; SQLite's own
  pattern (in-place conversions, unlocking several locks with one call, the whole-file
  unlock) leaks 160-1086 bytes of P0 per transaction (p_leak). The lock file is never read or
  written, so its descriptor's EOF write-back does no harm. The lock can't be on the database
  file itself: a writable C RTL descriptor corrupts its EOF (Q6), and a read-only one can't
  take write locks (`O_RDWR` with `fac=get` is refused).
- (b) **The lock manager directly** (`$ENQ`, one resource per SQLite lock byte). No extra
  file, no C RTL in the path. But a system-wide resource needs SYSLCK (p_lkns:
  `%X28F4` NOSYSLCK without it); without it the locks are only seen within the UIC group, so
  the PHP pool's account and a CLI user in another group would not exclude each other:
  silent corruption. Workable only with SYSLCK on every image (INSTALL /PRIVILEGED for main
  images; not possible for the shareable image) or a documented same-group rule.
- (c) **Dot-file locking** (SQLite's `unix-dotfile` idea: create/delete a lock file): no
  shared readers, so every reader would block the others; poor for a web pool.

Recommendation: **(a)**.

**As built (Phase 1):** the lock file's bytes are not SQLite's: PENDING is byte 0,
RESERVED byte 2, the SHARED range bytes 4-513. With SQLite's adjacent bytes
(0x40000000, +1, +2) the C RTL leaked 898 bytes of P0 per write transaction even with
exact pairs (PORTING_LOG #7); with the gaps, nothing on any path. Every VMS VFS that
shares a database must use this layout, so it is fixed from the first kit on. The RMS and
ACP blocks are allocated with `_malloc32` (clang) and refused above 2 GB (#9).

Open point: one test with two accounts in different UIC groups (e.g. the user's and the
LIGHTTPD account) that the C RTL's locks exclude across groups too; it needs the user to run
one side.

## D6. File names and versions

**Status:** approved by the user (2026-10-18).

ODS-5 takes SQLite's names (`x.db-journal`, `x.db-wal`, `Misc.Two.db`; p_misc). With the C
RTL, `O_TRUNC` creates a new version (p_misc); the VFS avoids this (D5: opens existing
files, truncates by EOF) and `xDelete` removes every version.

## D7. The VSI C aggregate bug

**Status:** approved by the user (2026-10-18).

The community kit reports `SUM()`, `AVG()` and `TOTAL()` miscompiled by VSI C on x86. Built
with VSI C V7.7-003 (`/FLOAT=IEEE/IEEE=DENORM/OPTIMIZE`), 3.54.1 gave the host's results for
them and for the other recon checks (integers, reals, NULLs, a 100,000-row CTE): no sign of
the bug with this compiler. The Phase 2 corpus compares every result with the host to catch
any miscompilation.

## D8. The cost of a read transaction

**Status:** (1) as built (2026-10-20, Phase 2); (2) option (b) chosen by the user
(2026-10-20), as built.

speedtest1 spent 149 of its 182 s in tests 410 and 510: 17,500 autocommit SELECTs each,
~4.3 ms per read transaction where Linux takes ~8 µs. p_cost timed the primitives on the x86
node: an ACP call ~0.62 ms (reading attributes and looking up a name cost the same), `$QIO`
read 0.28 ms, fcntl lock+unlock 0.16 ms, `sys$open` of a missing file 1.15 ms (of an existing
one, 2.7 ms), `access()`/`stat()` 1.3 ms. Per read transaction the VFS made 2 ACP reads of
the end of file (lock, `xFileSize`), SQLite 2 `xAccess` calls (`-journal` for a hot journal,
`-wal` in `pagerOpenWalIfPresent`), plus 4 fcntl calls and the counter's `$QIO`.

**(1) The end of file is read once per lock, and not at all when the file is as last seen.**
While a connection holds SHARED or more no other process can change the database, so
`xFileSize` and `xRead` use the end of file read when the lock was taken (`eofLocked`). It is
not read at all if block 1 (already read for the cache's change counter) shows the same
counter *and* a header page count × page size equal to our end of file. The counter alone
is not enough: rolling back a hot journal restores page 1, counter included, while
truncating the file (PORTING_LOG #19, mptest crash01). A dead writer's additions not yet
rolled back can leave our end of file short; SQLite rolls back before reading, and the end of
file is read again whenever the connection goes from SHARED to RESERVED or EXCLUSIVE.
Result: 0 ACP calls per read transaction, ~2.96 ms; speedtest1 132.5 s (was 182.4).
Alternative: read the header at each lock as before (correct, 1.2 ms slower per transaction).

**(2) The two `xAccess` calls (~2.3 ms of the remaining ~3 ms).** Options:
- (a) `SQLITE_OMIT_WAL` (the D4 WAL question): no `-wal` check, −1.15 ms.
- (b) `xAccess` by an ACP lookup of the name in the directory, on a channel assigned to the
  device, instead of an RMS open: ~0.65 ms each, −1.0 ms for the two; no protocol change.
- (c) A counter shared between processes (in a mapping of the lock file) that writers bump
  when they take RESERVED, so a reader can skip the `-journal` check while no writer has
  run since one was seen absent: −1.15 ms, but the lock file joins the protocol every VMS
  VFS must follow, and after a power failure a persisted "clean" value must never hide a
  hot journal. The lock manager can't carry it: without SYSLCK its resources are per UIC
  group (D5).
Recommendation: (b), and (a) only as part of the WAL decision.

**As built, (2) (b):** p_acclk showed the ACP takes a name as the directory holds it, finds it
whatever its case, and returns the end of file in the same call, but refuses ODS-5's extended
names (`acc.two.db`: BADFILENAME; a space: BADFILEVER), escaped or not. So `xAccess(EXISTS)`
uses one ACP lookup (`$PARSE`, `$ASSIGN` of the device, `IO$_ACCESS` by name in the directory,
`$DASSGN`: ~0.75 ms) when `$PARSE` escaped nothing and the name part has no dot, and the
spec is no search list, wildcard, node or quoted name; anything else, and any ACP status but
success or no-such-file, goes to the RMS open as before. SQLite's own names
(`x.db-journal`, `x.db-wal`) take the fast way. The channel is not kept between calls (it
would be one more thing holding the device). Result: ~2.13 ms per read transaction;
speedtest1 101.0 s (132.5 s with (1) alone).
